# 歸類規則

決定程式要放進哪個國家、城市、鄉鎮。格式見 `schema.md`，說明寫法見 `writing.md`。

## 三層是什麼

| 層 | 是什麼 | 怎麼判斷 | 常見大小 |
|---|---|---|---|
| 國家 | 一個業務系統或產品區塊 | 業務人員會把它當成一個「系統」來稱呼；有自己的使用者或目標 | 2–10 個城市 |
| 城市 | 系統裡的一個業務能力 | 圍繞同一組資料（實體、資料表），可以交給一個小組負責 | 2–15 個鄉鎮 |
| 鄉鎮 | 一個功能點 | 一個使用者操作、一個排程或事件觸發的背景作業，或一組有獨立程式的業務規則 | 1–5 支 API＋相關畫面 |
| 鎮民 | 鄉鎮裡的一個項目 | 同一個操作裡的欄位、選項或類別，各自有自己的規則 | 0–10 個 |

大小只是參考。超出範圍時先想想是不是切得太粗或太細，但不要為了湊數硬拆或硬合。

## 鄉鎮怎麼切

- **用業務語言命名**：「點數扣除」「資料集權限設定」，不要用類別或方法名稱。
- **寧可粗一點**：同一個畫面、同一個操作流程，就是一個鄉鎮。
- **要拆開**：觸發方式不同（使用者操作和排程）、操作的角色或權限不同、走的是不同的流程。
  例：點數的「累積」（訂單完成時觸發）、「扣除」（結帳時操作）、「到期」（每日排程）、「查詢」（會員查看）觸發方式都不同，所以是四個鄉鎮。
- **要合併**：同一個畫面上對同一筆資料的新增、修改、刪除 → 合成一個「X 維護」或「X 修改」。
- **各欄位、選項有自己的規則時，用鎮民表示，不要拆成鄉鎮**：
  例：姓名、生日、地址在同一個「個人資料」頁修改，就是一個鄉鎮「個人資料修改」，姓名、生日、地址是它的三個鎮民，生日「只能改一次」這類規則寫在鎮民上。
  例：一般會員、VIP 是「等級權益」這個鄉鎮的兩個鎮民。

## 鎮民

- 鎮民是鄉鎮裡的欄位、選項、類別或子步驟，只有 `name`、`rules`、`evidence` 三個欄位，沒有 ID。
- 只在項目各自有規則、值得單獨列出時才寫；沒有特別規則的欄位不用列。
- 鎮民的 `evidence` 寫該項目專屬的程式位置（例如驗證生日的方法）；共用的程式位置寫在鄉鎮的 `evidence`。
- **選 `type`**：
  - `operation`：使用者在畫面上或透過 API 主動做的事
  - `job`：排程、事件處理、訊息佇列消費者等背景作業
  - `rule`：沒有獨立操作、但有自己程式的業務規則（例如會員等級的權益定義）
- **evidence 至少 1 筆**，盡量涵蓋「畫面 → API → 邏輯 → 資料」這條線上最重要的位置，通常 2–5 筆就夠。
- **前後端屬於同一個功能時放在同一個鄉鎮**：畫面放 `screens`，API 放 `endpoints`。inventory 裡 `api-call` 的 `pairedWith` 會告訴你前端呼叫的是哪支後端 API。

## 國家和城市怎麼切

- **先參考專案已有的邊界**：模組（ABP module、.csproj、Python package）、資料夾、API 路由前綴（`/api/knowledge/...`）、前端選單或路由。
- **最後依業務判斷，不依技術分層**：Controller、Service、Repository 分在不同資料夾時，要按功能橫向收在一起，不要切成「Controller 城市」「Service 城市」。
- **模組不一定等於國家**：模組很小 → 可以只是某個國家裡的一個城市；模組很大 → 可以拆成好幾個國家。
- **國家的順序**：使用者最常用的放前面，`infra` 放最後。

## 基礎設施（`infra`）

`infra` 是一個一般的國家，同樣有城市和鄉鎮，只是說明可以短一點。

放這些：
- 驗證、授權的底層機制（token 處理、middleware、權限定義）
- 共用元件、工具函式、base class
- 健康檢查、日誌、設定、資料庫遷移
- 框架範本產生的範例程式（例如 ABP 的 `Samples/`、`ExampleController`）

不放這些：
- 使用者看得到的功能，即使技術上很底層。例如「註冊」「登入」「忘記密碼」是業務功能，應該放在帳號相關的國家。

## 三種專案型態

`config.json` 的 `parts` 決定型態：

| 型態 | 鄉鎮的 `screens` | 鄉鎮的 `endpoints` | 說明要多寫什麼 |
|---|---|---|---|
| 前後端 | 有 | 有，必須是 inventory 裡的 endpoint | — |
| 純前端 | 有 | 填前端呼叫的外部 API（來自 `api-call`），不需要存在於 inventory 的 endpoint | 資料來自哪個外部服務 |
| 純後端 | 沒有 | 有 | 誰會呼叫這支 API（前端團隊、其他系統、排程） |

## ID

- 用業務意義命名：`member.points.accrue`，不要用 `member.points.point-service-accrue`。
- 一個城市裡的鄉鎮 ID 不可重複；整份地圖的 ID 都不可重複。
- **ID 一旦建立就不能改。** 要改名就改 `name`。
- 鄉鎮搬到別的城市時保留原 ID，前綴和新城市不一致是允許的。
- 不可使用保留字 `uncharted`。

## 覆蓋率

- inventory 裡的 `endpoint`、`route`、`page` 都應該被某個鄉鎮涵蓋。
- 真的不屬於任何業務功能的，放進 `infra`，不要放著不管。
- 看不懂用途的，先放進最接近的城市，並在說明裡寫「用途待確認」。不要編造用途。

## 更新模式的原則

- **只改工作清單上的鄉鎮**，其他鄉鎮的內容完全不動（連空白和順序都不要改）。
- 新功能先歸到現有城市；至少 2 個鄉鎮放不進任何現有城市時，才開新城市。
- 鄉鎮的程式全部被刪除時，刪除這個鄉鎮；城市沒有鄉鎮時，刪除城市檔並更新國家的 `cities`。
- 鄉鎮說明有變動時，檢查所屬城市的說明是否還正確；城市說明有變動時，再檢查國家。
- 不可修改 `overrides.json`。

## 安全

- 不要讀 `config.json` 裡 `exclude` 排除的檔案（`.env`、`*secrets*`、憑證）。
- 不要把密碼、連線字串、金鑰、token、真實個資寫進任何說明。
- 不要大段貼程式碼；說明裡用 `` `識別字` `` 提到名稱就好。
