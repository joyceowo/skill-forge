# 說明寫法

三層各有不同的讀者。同一份地圖，SA 只看國家，SD 看到城市，PG 一路看到鄉鎮和鎮民。

## 共通原則

- 繁體中文、台灣用語：程式、資料、檔案、設定、資料表、介面。
- **只寫從程式讀到的事實。** 無法確認的寫明待確認事項與已查範圍，不以「未看到」推論整個功能不存在該規則。
- 程式識別字用反引號：`` `MemberProfileService` ``。
- 程式有數字、門檻、時間時寫出實際值，例如「30 天」，不要寫「一段時間」；沒有數值的規則不補數字。這類共通內容優先放進鄉鎮的 `rules`。
- 用詞依照 `glossary.json`；遇到新的業務詞彙，先加進 glossary 再使用。
- 不要行銷語氣（「強大」「無縫」「一站式」）。

## 國家：寫給 SA

**讀者**：系統分析師、PM、業務窗口。

**要寫**：這個系統解決什麼業務問題、誰在用、帶來什麼價值；和其他系統的關係用一句帶過。

**不要寫**：類別名稱、API 路徑、技術架構。

**長度**：2–4 句，約 100–250 字。

✅ 好的寫法：
> 管理會員註冊後的個人資料、會員等級與點數回饋。會員可以自行修改資料、查詢點數；客服人員可以協助修改資料。系統依消費金額自動評定等級，等級再決定點數回饋倍率，用來提高回購率。

❌ 不好的寫法：
> 本模組包含 `MemberProfileController`、`TierEvaluationJob`、`PointService`，使用 EF Core 存取 `Members` 資料表，提供強大的會員管理功能。

（寫了技術細節，SA 看不懂；「強大」是行銷語氣；沒說解決什麼問題。）

## 城市：寫給 SD

**讀者**：系統設計師、資深工程師。

**要寫**：
- 負責的範圍
- 主要流程怎麼設計：同步或非同步、排程、事件
- 主要資料（也列在 `data`）
- 依賴哪些其他城市、為什麼（也列在 `dependsOn`）
- 設計重點：權限、交易、快取、稽核等

**可以寫**：類別名稱、資料表、API 群組。**不要寫**：逐行的實作細節。

**長度**：3–6 句，約 150–350 字。

✅ 好的寫法：
> 以交易流水 `PointTransactions` 記錄每一次點數異動，`MemberPoints` 只存目前餘額，由流水彙總而來，方便對帳與追查。點數累積在訂單完成事件中處理，扣除在結帳時同步呼叫，到期由每日排程批次處理。回饋倍率依會員等級決定，因此依賴會員等級模組。

❌ 不好的寫法：
> 處理點數相關功能，包含累積、扣除、到期、查詢。

（只是把鄉鎮名稱再列一次，沒有說明設計。）

## 鄉鎮：寫給 PG

**讀者**：要修改或除錯這個功能的工程師。

**要寫**：
- 怎麼觸發：哪個畫面、哪個排程、哪個事件
- 主要處理、條件與結果，用商業文字說明
- API、檔案、函式與修改定位留在 screens／endpoints／evidence 的技術參考；正文不夾帶行號或逐項程式框
- 共通商業規則放在 `rules`：記錄程式實際存在的條件、限制、計算與例外處理；不要求每種類型都有。每條以一句為主，保留完整條件與實際數值，不為壓到 40 字而省略判斷分支。

**長度**：2–5 句，約 80–250 字。

✅ 好的寫法：
> 會員在結帳頁選擇使用點數折抵。系統檢查可折抵額度後，優先扣除最早到期的點數，保存扣點紀錄並更新餘額。

搭配的 `rules`：
```json
[
  {"id": "member.points.redeem.rate", "text": "1 點折抵 1 元", "status": "confirmed", "evidence": [{"file": "api/Points/PointPolicy.cs", "symbol": "PointPolicy", "role": "config"}]}
]
```

❌ 不好的寫法：
> 這個功能用來扣點數，使用者可以在畫面上扣點數。

（沒有說明觸發、處理與結果；也没有具體規則。程式位置應由 evidence 提供。）

### 內容完成核對

每國標記 `done` 前，以及更新既有文件時，在本輪要求的分析／更新範圍內核對各鄉鎮：

- `summary` 用純商業文字說清楚觸發、主要處理與結果；只有 API 或檔名清單不算流程說明。
- 對照相關處理程式與必要的呼叫鏈，將會影響結果的已查得條件、限制、計算、例外及狀態變更寫入 `rules`，不要只留在摘要或聊天回覆。數值與分支須能由 `evidence` 定位的程式核對，不能拿範例當事實。
- 同一流程內欄位、選項各自的規則寫入 `residents`，共通規則留在鄉鎮。每條新規則用物件保存穩定 ID、確認狀態與 evidence，多個來源可共用；鎮民亦可保留分組 evidence。條件與其來源對應不能只留在聊天中。
- 已查到的資料讀寫寫入 `reads`／`writes`，名稱與城市 `data` 一致（同一資料表在各城市寫法相同才查得到）。舊文件缺這兩欄而程式有資料存取時，屬於內容缺口；查不到實際名稱時保留待確認，不為過關填入。
- `rules: []` 本身不能證明「沒有規則」，也不一定是缺漏。先讀相關程式，確認沒有共通規則可記錄後可保留空陣列；可在 `summary` 或交付回報說明查核範圍。無法確認的仍列待確認，不捏造規則，也不宣稱全功能無規則。
- 比較已查得的內容與現有文件，只補缺漏或修正受影響內容。HEAD 未變、舊進度為 `done` 或工具驗證成功，都不能掩蓋已發現的缺項；保留其他文字、節點 ID 與人工 overrides。

逐條規則格式與 rule-review 核對見 [business-analysis.md](business-analysis.md)。每條候選留下已寫入／非商業／待確認結果，不以解析成功代替閱讀；空規則合法，但不可用空值掩蓋已查得條件。單純匯出既有地圖不因此擴大成全案重分析。

## 鎮民

只描述從程式查證的限制，不推測商業動機，例如「避免重複領生日禮」必須另有程式證據。

鎮民不另寫摘要，使用名稱、規則及可定位的證據。名稱用畫面上或業務上的叫法（「生日」「VIP」），規則和鄉鎮的 `rules` 一樣，保留完整條件與程式中的實際數值。
鄉鎮的 `summary` 要提到有哪些鎮民，但不用重複鎮民的規則。

```json
"residents": [
  { "name": "姓名", "rules": [{"id": "member.profile.name.length", "text": "長度 2–50 字", "status": "confirmed", "evidence": [{"file": "api/Member/Profile/MemberProfileService.cs", "symbol": "MemberProfileService.UpdateNameAsync", "role": "logic"}]}] }
]
```

## 三種專案型態的補充

- **純前端**：鄉鎮說明寫出使用者操作與已知結果，外部 API 放入 endpoints，未取得的後端限制標為待確認。
- **純後端**：鄉鎮說明要寫誰會呼叫這支 API（前端、其他系統、排程）。
